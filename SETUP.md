# SETUP.md — план первоначальной миграции (одноразовый)

> Это одноразовый чеклист, не постоянные правила. В отличие от `AGENTS.md`, Cline **не подхватывает
> этот файл автоматически** — на каждом шаге явно говорите агенту, что делать, и проверяйте результат
> перед тем как двигаться дальше. После завершения всех шагов файл можно удалить.

## Шаг 0. Структура репозитория

- [x] Переместить текущий фронтенд (React + FSD) в `/webapp`, не меняя его внутреннюю структуру и
      логику — только физическое перемещение файлов + правки путей в конфигах (vite, tsconfig,
      deploy-скрипты), если понадобятся.
- [x] Создать `/backend` — пустой Nest-проект через `nest new backend` (или `nest new .` внутри
      папки).
- [x] Проверить, что оба проекта (`/webapp`, `/backend`) независимо стартуют локально
      (`npm run dev` для фронта, `npm run start:dev` для бэка) без ошибок на этом этапе.

## Шаг 1. База данных локально

- [x] Добавить в `/backend` `docker-compose.yml` с сервисом `postgres` (образ, порт 5432, volume
      для персистентности).
- [x] `docker compose up -d`, убедиться, что БД поднялась и доступна.

## Шаг 2. Prisma

- [x] Установить Prisma (`prisma` + `@prisma/client`), `npx prisma init`.
- [x] В `schema.prisma` настроить `datasource` на `postgresql`, `DATABASE_URL` в `.env` указывает на
      локальный docker-контейнер.
- [x] Описать первые модели на основе существующих сущностей из Firebase (`src/shared/types.ts` в
      `/webapp`): `User`, `Product`, `Brand`, `Category` — но уже как **нормальные relations**
      (foreign keys), а не денормализованные вложенные объекты, как было в Firestore.
- [x] Прогнать первую миграцию (`prisma migrate dev --name init`).

## Шаг 4. Первый модуль — эталон архитектуры (Categories)

Категории выбраны первыми специально: самая простая сущность (`id`, `name`), без сложных связей —
удобно один раз аккуратно пройти всю структуру слоёв, прежде чем повторять её для более сложных
сущностей (Products).

- [ ] Реализовать модуль `categories` строго по структуре из `AGENTS.md`
      (`domain/` → `application/` → `infrastructure/` → `presentation/`), включая интерфейс
      репозитория + Prisma-реализацию.
- [ ] Эндпоинты: получить список категорий, создать категорию (с проверкой на дубликат имени — эта
      бизнес-логика должна жить в `application/categories.service.ts`, а не в контроллере и не в
      репозитории).
- [ ] Юнит-тест на `CategoriesService` с замоканным репозиторием (проверить как минимум сценарий
      "нельзя создать дубликат").

## Шаг 5. Авторизация (минимально)

- [ ] Guard, который проверяет Firebase ID Token через `firebase-admin` и кладёт `uid` пользователя в

- [ ] Применить Guard к модулю `categories` (категории привязаны к пользователю).

## Шаг 6. Первая сквозная интеграция с фронтом

- [ ] На фронте (`/webapp`) заменить содержимое одной конкретной функции —

      Firestore. Сигнатура функции не меняется, меняется только реализация внутри.
- [ ] Проверить вручную в браузере: логин через Firebase (как раньше) → список категорий приходит
