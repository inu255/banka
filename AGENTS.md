# AGENTS.md — backend (banka)

## Что это за проект

Это **учебный** бэкенд-проект. Основная цель — не просто получить рабочий код, а
**разобраться, как работает каждая часть системы**. Приоритеты в таком порядке:

1. Понятность и объяснимость кода — выше, чем скорость написания.
2. Правильная архитектура (DDD-лайт + repository pattern) — выше, чем "просто заработало".
3. Покрытие тестами ключевой бизнes-логики.
4. Идиоматичный NestJS-код, без самодельных решений там, где у фреймворка уже есть стандартный паттерн.

**Правило для агента:** при добавлении любого нетривиального куска (новый модуль, новый
паттерн, нестандартное решение) — обязательно сопровождать код кратким объяснением **в чате**
(не только в code comments): что это, зачем это нужно именно здесь, какие есть альтернативы и
почему выбран именно этот вариант. Если решение стандартное и очевидное (обычный CRUD-метод) —
объяснение не нужно, не разводить воду.

## Контекст проекта

- Приложение для учёта косметики: пользователь ведёт список продуктов (когда открыл, бренд,
  категория), может добавлять свои категории и общие для всех бренды.
- Фронтенд (`/webapp`) — React + FSD, сейчас всё на Firebase (Auth + Firestore).
  **Фронтенд не трогаем**, кроме постепенной замены прямых вызовов Firestore на вызовы нашего API
  внутри уже существующих функций в `features/*/api.ts` и `entities/*/api.ts`. Реализация внутри
  этих функций (fetch к нашему API вместо Firestore SDK) — тоже задача бэкенд-агента, когда
  соответствующий endpoint готов.
- Бэкенд (`/backend`) — то, что мы пишем сейчас, на NestJS.
- В перспективе возможен React Native клиент — учитывать это при проектировании API (не завязывать
  контракты на что-то специфичное для веба).

## Стек

- **NestJS** — фреймворк бэкенда.
- **PostgreSQL** — база данных.
- **Prisma** — ORM. Схема — единый источник правды о структуре БД. Менять структуру таблиц
  **только** через `prisma migrate dev`, никаких ручных ALTER TABLE и никаких правок схемы БД в обход
  Prisma.
- **Firebase Admin SDK** — верификация Firebase ID Token на входящих запросах (см. раздел
  "Авторизация").
- **Jest** — тесты (юнит + при необходимости e2e), идёт из коробки с Nest.
- **OpenAPI (`@nestjs/swagger`)** — автогенерируемая схема API из DTO и декораторов контроллеров.
  Даёт интерактивную документацию (Swagger UI) для ручной проверки эндпоинтов и, в перспективе,
  базу для автогенерации типизированного клиента на фронт (и на будущий React Native клиент) —
  вместо ручного дублирования типов между `/backend` и `/webapp`.

## Архитектура (DDD-лайт + Repository pattern)

Полный DDD (агрегаты, value objects, domain events и т.д.) — избыточен для проекта такого размера.
Берём **упрощённую** версию, достаточную чтобы отделить бизнес-логику от деталей БД и явно увидеть
слои. Внутри каждого фичевого модуля Nest (`src/modules/<domain>/`) придерживаемся такой раскладки:

```
src/modules/products/
  domain/
    product.entity.ts        # доменная модель — чистый TS-класс/интерфейс, без Prisma-типов
    product.repository.ts    # ИНТЕРФЕЙС репозитория (abstract class или interface + token)
  application/
    products.service.ts      # бизнес-логика, use cases. Знает только про domain + интерфейс репозитория
  infrastructure/
    prisma-product.repository.ts  # РЕАЛИЗАЦИЯ репозитория через PrismaService
  presentation/
    products.controller.ts   # HTTP-слой: DTO, валидация, маппинг в/из domain
    dto/
      create-product.dto.ts
  products.module.ts
```

Ключевые правила:

- **`application/*.service.ts` никогда напрямую не импортирует `PrismaClient` и не знает про
  Prisma.** Он работает только с интерфейсом репозитория (`ProductRepository`), который
  инжектится через DI-токен. Это и есть смысл repository pattern здесь: захотим сменить Prisma на
  что-то другое (или замокать в тестах) — меняем только `infrastructure/`, `application/` не трогаем.
- **`domain`-модели — не то же самое, что Prisma-модели.** Даже если поля совпадают 1-в-1 —
  разделяем их явно (отдельные типы), чтобы бизнес-логика не была случайно завязана на структуру
  таблиц БД.
- DI-токен для репозитория регистрировать в модуле явно:
  ```ts
  {
    provide: 'ProductRepository', // либо Symbol/injection token
    useClass: PrismaProductRepository,
  }
  ```
- Не плодить слои ради слоёв. Если фича совсем тривиальная (например, простой CRUD без бизнес-правил) —
  всё равно соблюдаем структуру (для единообразия и обучения), но не пытаемся искусственно найти
  "бизнес-логику" там, где её нет.

## Общая инфраструктура

- `PrismaService` — обёртка над `PrismaClient` с `onModuleInit`/`onModuleDestroy`
  (как разбирали ранее), лежит в `src/infrastructure/prisma/prisma.service.ts`, отдельный
  `PrismaModule`, `@Global()`, экспортируется во все модули.
- Общие доменные типы (если понадобятся) — `src/shared/`.

## Docker и локальная разработка

Хостинг для деплоя пока **не выбран** — не привязываемся заранее ни к какому провайдеру, чтобы не
переделывать конфиги, когда решение будет принято. Сейчас важна только локальная разработка:

- **Фронт (`/webapp`) и бэк (`/backend`)** — запускаются локально обычным образом (`npm run dev` /
  `npm run start:dev`), без Docker.
- **Postgres** — поднимается в Docker через `docker-compose.yml` в `/backend`: один сервис
  `postgres`, порт наружу, volume для персистентности данных между перезапусками. Это единственное,
  что реально нужно от Docker на данном этапе.
- **CI:** базовый GitHub Actions workflow на пуш/PR — `lint` + `test`. Простой шаблонный
  `.github/workflows/ci.yml`, без деплоя (деплой настроим отдельно, когда определимся с хостингом).

Когда хостинг будет выбран — донастроить деплой отдельной задачей (может понадобиться Dockerfile
для самого приложения, конфиг конкретной платформы и т.д.) — это не требует изменений в архитектуре
приложения, только в конфигурации деплоя.

## Авторизация

**Сейчас:** фронт логинится через Firebase Google OAuth, это не трогаем. Бэкенд пока опирается на
Firebase для проверки личности пользователя, а не на свою систему логина/паролей.

**В перспективе:** переход на свою JWT-авторизацию (возможно, в сочетании с OAuth). Детали
реализации (и текущей, и будущей) разбираем с агентом по ходу дела — здесь сознательно не фиксируем
конкретный план, чтобы не тащить в код решения, которые не до конца понятны на момент написания.

## Тесты

- Юнит-тесты — обязательны для `application/*.service.ts` (бизнес-логика). Репозиторий в тестах
  мокается (это и есть главный практический смысл repository pattern — сервис тестируется без
  реальной БД).
- Для репозиториев (`infrastructure/`) — по возможности интеграционные тесты на тестовой БД
  (например, через `docker-compose` с отдельным Postgres для тестов), но это не блокер для старта —
  можно добавить позже, когда основной каркас будет готов.
- Не гнаться за 100% покрытием — цель научиться писать осмысленные тесты на ключевую логику,
  а не покрыть тестами геттеры.

## Стиль работы агента

- Если для реализации есть несколько разумных подходов — **кратко** предложить варианты с
  плюсами/минусами перед тем как писать код, а не молча выбирать один.
- Не добавлять зависимости/паттерны "про запас" (микросервисы, очереди, кэш и т.п.) без явного
  запроса — проект сейчас учебный и небольшой, оверинжиниринг мешает, а не помогает обучению.
- При создании миграций Prisma — объяснять, что меняется в схеме и почему.
- Код на TypeScript, строгая типизация, без `any` без крайней необходимости (если `any` всё же
  нужен — объяснить, почему тип нельзя было указать точнее).
